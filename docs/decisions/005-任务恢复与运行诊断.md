# 决策005：任务恢复与运行诊断

日期：2026-11-03。状态：已实现并自动验证，待人工验收。

## 问题与取舍

原Worker只对业务处理异常做重试，领取任务、续租、发布或记录失败时的数据库异常可能逃逸至主循环并终止进程。浏览器能看到任务等待，却不能区分Worker无活动与队列正常等待。

本批保留原有数据库任务队列、300秒租约、最多3次领取及单事务发布，增加数据库故障的主循环退避恢复和心跳诊断。暂不引入消息中间件、常驻线程或分布式监控系统，适合本机课程原型。

## 恢复规则

- 主循环捕获SQLAlchemy数据库异常，按1、2、4、8、16、30秒退避，后续最多30秒；成功一轮后重置计数并记录恢复事件。
- 处理过程中数据库结果不确定时，不再尝试将任务改成业务失败。若发布事务未提交，保留processing状态，租约到期后可被重新领取；如果已提交，任务为succeeded，不重复领取。
- 原子发布继续覆盖片段、版本状态、当前版本指针及任务状态。模型分批结果先留在内存，全部成功才发布；中途故障不写入部分索引。
- 可重试向量错误仍执行任务级5秒、10秒等待，最多3次领取；数据库连接恢复等待与任务级重试是不同机制。旧进程持有失效租约时不能续租或发布。
- `--once` 遇数据库故障返回退出码1，便于脚本发现；常驻模式持续重连。未捕获的程序错误仍可能终止进程，心跳只能帮助发现，不能替代进程管理。
- API及Worker数据库连接建立和连接池等待设置为5秒。该值不是整个请求或整个SQL执行的总超时。未新增数据库statement_timeout或自动重试HTTP写请求。

## 心跳与权限边界

迁移 `0004_worker_health` 增加 `worker_heartbeats`。每个Worker进程使用随机ID，空闲轮询、领取及处理批次更新心跳；正常退出尽力标记stopped，强制退出以心跳过期识别。原Worker仍是单任务顺序处理，长解析可能延迟心跳，不增加后台心跳线程。

`GET /api/projects/{project_id}/ingestion-status` 必须验证当前项目成员身份。返回最近90秒是否存在未停止Worker心跳，以及当前项目有效资料全部版本的任务数和最早待完成任务时间。全局只暴露“近期是否有活动”和最后活动时间，不返回Worker ID、其他项目任务、文件名、密钥或资料正文。心跳不绑定项目，因为现有Worker共用队列、可以处理所有项目。

心跳是近期活动信号，不能证明某个任务进展或模型服务健康；队列为0也不是完整系统健康证明。撤下的资料不进入任务统计，已发布资料的历史失败任务仍可能计入失败数。心跳旧行目前保留，未实现自动清理。

## 展示与观测

资料页显示近期心跳、当前项目等待/处理中/失败数、最早待完成任务、自动重试不早于时间及处理中租约期限。每3秒刷新；无心跳时给出检查Worker和数据库的提示，不声称已确定故障原因。

新增入库成功日志字段：`parse_ms`、`embedding_ms`、`publish_ms`、`total_ms`，通过task UUID关联任务，不记录正文和路径。数据库异常只记录异常类型及退避秒数，不记录异常文本、SQL或凭据。API错误带追踪编号，资料页显示该编号。修正资料页在初次加载尚未完成就切页时，仍可能创建轮询定时器的问题。

自动验证包含并发上传与并发发布、发布事务注入数据库异常、租约恢复、分批向量故障、重连退避上限、API数据库错误安全提示、项目隔离和模型超时；详见 [第五批验收](../第五批验收.md)。没有在用户正在使用的数据库上执行停库或断网实验。
