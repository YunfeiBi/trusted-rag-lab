## 1. 项目介绍与最容易被追问的边界

### 1）用一分钟介绍知序

**练习回答：** 知序是科研团队的资料管理和引用问答课程项目，后端用 Python、FastAPI、PostgreSQL 和 pgvector。原流程是授权检索后生成答案并核对引用。本次加入 LangGraph 编排的检索、写作、审查三个角色：检索角色规划查询并请求服务端授权搜索工具，写作角色生成结构化答案，审查角色检查证据支持关系，并选择通过、改写、重新检索或拒答。流程最多两轮、六次角色模型调用；权限或资料变化会停止展示。AI 辅助实现的范围会如实说明，自动测试和离线场景检查不能代表真实回答质量。

**追问：** 你自己做了什么？不要把上面整段当成个人独立编码声明。准备你真实做过的需求取舍、读过的函数、修改过的规则、亲自复现过的故障和测试记录。

### 2）这算多 Agent，还是工作流？

这是受控的多角色 Agent 协作工作流：角色有不同提示和职责，检索角色能提出搜索动作，审查结果决定下一步，而不是三次固定顺序调用。它的控制边界由代码固定，不是任意自主规划的通用多 Agent 团队。LangGraph 官方也区分预定路径的 workflow 与动态决策的 agent；能说清这个边界比争名称更重要。

**不能声称：** 已实现通用任务规划器、任意工具自主选择、长期记忆、自主多人协商或分布式 Agent 执行。

### 3）为什么需要三个角色？单模型不行吗？

基础问答就可以用单次生成，本项目保留了这个基线。拆角色是为了将查询规划、写作和独立提示下的审查分开，并显示失败原因和交接路径。代价是调用次数、延迟和成本上升；如果真实评测没改善，就不能说拆分一定更好。最有意义的对照是同一题集上的基础模式和协作模式。

### 4）三个角色具体输入输出是什么？

| 角色 | 输入 | 结构化输出/动作 | 不能做什么 |
|---|---|---|---|
| 检索 | 原问题、有限的反馈码 | `RetrievalPlan(action, query)`；请求 search 或 abstain | 指定别的用户/项目、执行 SQL/shell |
| 写作 | 原问题、当前授权证据、反馈码 | `AnswerDraft(answerable, claims)`；每项含证据编号和原文摘录 | 创造证据、直接发布未经验收答案 |
| 审查 | 原问题、证据、结构化草稿 | `ReviewDecision(action, reason)` | 调用工具、修改权限、写最终答案 |

三个角色可复用同一个模型接口和模型名称。角色分离不等于用了三个不同基座模型，也不代表模型错误彼此独立。

### 5）你用了原生 function calling 吗？

当前用结构化 JSON 动作计划加服务端固定分发：Schema 只接受 search/abstain，搜索回调由后端绑定项目、用户、会话。没有使用供应商的原生 `tools/tool_calls` 协议。两者都需要服务端验证和执行授权；模型输出动作不是执行权限。这是面试时必须如实区分的点。

### 6）怎么防止无限循环？

`run_agent_workflow` 默认最多两轮处理、六次角色模型调用，另设 120 秒阶段预算。审查要求改写也消耗轮次；返回检索会增加轮次；引用或结构错误不能无限重试。调用前检查预算，结束路径明确。LangGraph 还设置递归步数上限作为防御，但它不是业务重试策略的替代品。

**陷阱：** 六次只统计检索规划、写作和审查的聊天调用。Embedding、Rerank 是搜索工具内部调用，不能把六次说成所有外部请求的上限。轮次是处理预算，不保证每轮都包含三个完整角色。

### 7）LangGraph 的 State、Node、Edge 是什么？

State 是节点间传递的状态；Node 是读状态并返回更新的函数；Edge 决定下一步。当前图状态保存轮次、反馈和路由，检索证据与草稿保留在一次请求独有的闭包中。条件边根据 route 去写作、审查、重新检索或 END。每个请求构建独立图实例，避免跨用户共享草稿。

**追问：** 为什么不把草稿写到检查点？当前优先避免持久化被拒绝草稿，因此未启用 checkpointer。不是 LangGraph 自动给本系统提供了断点续跑。

### 8）你的状态持久化到了哪里？进程挂了能恢复吗？

最终问答和脱敏的角色执行记录存到现有 `QuestionRecord.details`，不增加中间草稿列；`0010_agent_workflow` 迁移扩展了终态的数据库约束。执行中的图没有数据库检查点；请求中途进程崩溃不会从中间节点续跑，用户需要重新提交。文档入库 Worker 有自己的数据库任务、租约和恢复机制，不能混同为 Agent 图的恢复能力。

## 2. 审查、引用和失败处理：岗位核心追问

### 9）审查 Agent 通过，能保证没有幻觉吗？

不能。确定性校验检查结构、证据编号、摘录是否出自本次证据；审查模型再判断结论是否受证据支持，但模型可能误判，同模型的角色也可能重复同样的错误。还要人工标注、固定测试集和失败案例分析。正确表述是增加了一层验收，而不是消除了幻觉。

### 10）摘录是真的，为什么结论可能仍然错误？

原文“学生可申请补助”，答案“所有学生都必定获得补助”，引用的字符串是真实的，结论仍扩大了条件。`validate_claims` 不做逻辑蕴含证明。审查负责尝试识别这种问题，人工评测才是质量证据之一。

### 11）审查不通过会发生什么？

- `rewrite`：证据足够、表达或结论有问题，把受控反馈码交回写作角色。
- `retrieve`：需要新证据，交回检索规划角色，再执行同一授权范围内的搜索。
- `refuse`：结束，返回安全提示，失败草稿不展示。
- 达到轮数上限：不继续调用，不把最后一个未经通过的草稿当答案。

理由使用有限枚举，不将审查模型的自由文本当成新的系统指令。写作角色拿到反馈码，不自动继承前一次被拒绝的草稿。

### 12）JSON mode 和 Schema 校验有什么区别？

JSON mode 主要约束 JSON 输出格式，不足以证明字段、类型及业务关系正确。Pydantic 检查字段、枚举、长度和跨字段关系：例如 `answerable=true` 不能配空 claims；accept 必须对应 accepted；禁止额外字段。合法 JSON、合法 Schema、合法引用、语义正确，是四个不同层次。

### 13）模型流式输出是不是更快？为什么现在不直接流式展示草稿？

流式能改善首字等待体验，不一定降低总计算时间。当前需要先完成结构和引用核验以及审查，直接展示草稿可能先泄露错误答案、撤回也晚了。可以先流式发送阶段状态，最终答案通过后再显示；本次页面展示的是完成后的执行记录，尚未实现实时事件流。

### 14）工具/模型超时怎么处理？

模型适配器将网络异常转成安全错误码；图在阶段前后检查总预算，每次聊天请求使用剩余预算与 45 秒中的较小值。当前同步 HTTP timeout 不是整个操作的绝对硬中断：HTTP 分阶段超时、搜索内部请求及数据库耗时仍有边界。生产可进一步增加独立任务期限、取消传播和统一预算。不要说“120 秒后一定强制杀死所有调用”。

### 15）哪些错误可以重试，哪些不能？

临时网络、限流、格式错误有时可重试，但要控制次数、退避和剩余预算；权限拒绝、参数非法、业务明确拒绝不能盲目重试。本次引用/结构错误可在两轮预算内要求重写；上游不可用通常直接安全结束。没有实现所有 HTTP 错误的自动重试矩阵，也未处理 Retry-After 的完整策略。

### 16）如何排查一个“回答失败”？

先看 trace_id、最终 status、角色事件和错误码；判断是未召回、模型不可用、结构非法、引用错误、审查拒绝还是资料变更。再复现最小输入，对照原文，修复单个环节并加回归测试。日志不打印 API key、完整草稿或原始资料。不要先通过放松校验把错误“修好”。

### 17）PDF 引用故障为什么只忽略空白？

PDF 可能在中文词内部插入换行，模型引用省略这些排版空白，旧规则会误拒绝。新规则只忽略 Unicode 空白，匹配非空白字符的连续序列，再根据位置恢复真实原文片段。改字、跳字、省略号和标点不同仍拒绝，至少 8 个非空白字符。不能模糊匹配到一段大概相似的内容就当引用正确。

### 18）调用次数、token、成本是一回事吗？

不是。长上下文的一次调用可能比多次短调用更贵；重试、Embedding、Rerank 也有成本。当前记录角色调用次数和阶段时间，没有完整聚合供应商 usage、token 和真实费用。下一步应保存模型名、输入/输出 token、价格配置版本和估算费用；不能声称已实现精确成本控制。

## 3. RAG 与权限：你必须懂的基础

### 19）RAG 的完整链路是什么？

资料上传 → 解析文本与位置 → 分块 → Embedding → 存储向量/元数据 → 查询编码 → 候选召回 → 融合/重排 → 组装证据 → 生成 → 校验 → 展示原文。入库是离线/后台处理，查询是在线处理，两条链路需分别计时和排错。

### 20）Embedding 和 token ID 的区别？

Token ID 是词表中的离散编号，编号相邻不意味着语义相近；Embedding 是模型学习到的向量。检索时查询和资料向量要处在兼容空间，通常使用同一模型及正确的查询/文档编码方式。相同维度不保证兼容，换模型往往需要重建索引。

### 21）余弦相似度 0.9 是 90% 正确吗？

不是。余弦是向量夹角关系，`dot(a,b)/(norm(a)*norm(b))`；它不是回答正确概率，也不能直接当根因概率。阈值需要依据特定模型和标注集校准，不能跨模型照搬。零向量不能正常算余弦，模型返回值还要检查维度、有限数和非零。

### 22）为什么关键词和向量要混合？RRF 是什么？

关键词对精确编号、名称和术语有用；向量对语义改写有用，两者分数尺度不同。RRF 按名次融合：对每路候选累加 `1/(k+rank)`，当前代码 k=60；它是排序融合，不是概率平均。还要去重、权限过滤和当前版本约束。

### 23）Rerank 与向量召回有什么区别？

召回从大量资料中找小批候选，强调速度；重排更细致地联合比较问题和候选文本，通常更贵，只对候选运行。先召回没找到的证据无法靠重排凭空补出。当前重排服务失败会保留融合结果，向量服务失败时混合模式可降级为关键词，纯向量模式则返回不可用。

### 24）chunk 太大/太小分别有什么问题？

太小丢上下文，太大稀释相关信息且增加 token。overlap 能减少边界断裂，但增大存储与重复召回。项目要保留页码/行号/章节和版本，方便追溯。选择大小应比较检索覆盖和答案质量，不是只记某个固定长度。

### 25）为什么不能只在检索前验一次权限？

模型调用较慢，期间用户可能退出、权限撤销、资料撤下或换版。检索前限制候选范围，外发前检查证据有效性，生成/审查后与保存前再次验证；历史读取也复核。身份和项目范围由服务器会话确定，不能相信模型输出中的权限字段。

**边界：** 检查不能撤回已经合法发送给外部服务的数据，跨时刻校验也不等于绝对消除全部并发窗口。需要明确外发同意、最小数据和更严格的一致性设计。

### 26）为什么模型调用时不能一直持有数据库事务？

长事务可能占用连接、延长锁/MVCC 快照寿命，且模型慢和失败不可控。取到必要资料后 rollback 释放事务，再调用外部服务；回来用短事务复核和保存。rollback 不会自动使已经加载的内容重新合法，所以必须显式查最新权限和版本。

### 27）提示词注入怎么处理？

资料里可能出现“忽略规则、泄露其他项目资料”等文字。提示词声明资料不可信，但提示本身不是安全边界。真正边界是工具白名单、Schema、服务端授权、固定项目作用域、没有 shell/SQL 工具、失败输出过滤。当前只读搜索流程没有给模型管理权限。

### 28）向量数据库为什么选 PostgreSQL+pgvector？有 HNSW 吗？

本项目的权限、版本和业务数据已在 PostgreSQL，同库便于联查和约束；pgvector 提供向量距离运算。当前不要直接宣称“用了 HNSW 毫秒检索”，必须先在迁移和 EXPLAIN 中确认。数据规模、索引类型、过滤选择率和召回率都需要测量。pgvector 支持近似索引不等于本项目已启用。

### 29）RAG 和微调怎么选？

经常变化、需引用和权限控制的资料适合检索；风格、固定行为和任务模式可考虑微调。微调不是可靠的数据库，也不自动解决最新知识和访问授权。当前没有本项目的 LoRA 训练成果，不能为贴岗位写“掌握微调”。

### 30）如何证明多 Agent 比基础 RAG 好？

固定问题集、文档版本、模型配置和标注标准，对比两种模式。分别统计证据召回、结论支持率、拒答准确性、端到端任务成功、延迟 p50/p95、调用次数与 token；把失败分成检索错、生成错、审查漏判。相同模型不能只对协作模式挑好案例。离线脚本的 8 个预设场景检查控制流，不能证明真实模型质量提高。

## 4. Python、FastAPI 与工程基础

### 31）`async def` 就能让阻塞请求不阻塞吗？

不能。协程要在 await 非阻塞操作时交出执行权；在 async 路由里调用同步阻塞 HTTP 仍可能阻塞事件循环。项目当前问答路由是普通 def，同步逻辑由框架在线程池运行；高并发仍受线程、连接池和模型配额限制。改异步要连数据库/HTTP 调用一起审查，不能只加 async 关键字。

### 32）协程、线程、进程怎么选？GIL 怎么回答？

网络 I/O 可用异步或线程；CPU 密集解析可考虑进程。常规带 GIL 的 CPython 中，多线程执行纯 Python CPU 代码的并行能力受限制，I/O 和释放 GIL 的扩展不同；还存在可选无 GIL 构建，不能说所有 Python 环境永远不能多核。项目的解析隔离和模型 I/O 是不同负载。

### 33）为什么可变默认参数危险？

`def f(items=[])` 的默认列表在函数定义时创建，调用间复用。用 `None` 并在函数内部创建新列表。类似地，不要把一个用户的草稿和 evidence 放到全局可变列表里，否则请求间串数据。

### 34）浅拷贝、深拷贝在 State 里有什么坑？

浅拷贝只复制外层容器，嵌套列表和字典仍可能共享。并行节点如果修改共享嵌套对象，可能覆盖更新；需要明确归并策略或不可变更新。当前没有图中并行分支，不应说用了 reducers 处理并行冲突。后续并行检索要设计去重、排序和预算。

### 35）`try/finally` 为什么出现在 guard？

不管权限检查返回还是抛异常，都要释放当前数据库事务；因此用 finally rollback。异常不是全部吞掉：授权失败继续交给 API 返回 404，不伪装成“证据不足”。错误类型和用户提示要分层。

### 36）FastAPI Depends、Pydantic、SQLAlchemy 分别做什么？

Depends 提供身份、会话等依赖；Pydantic 校验请求和模型输出；SQLAlchemy 负责数据库访问与事务映射。校验请求合法不代表有业务权限，ORM 也不自动帮所有查询加项目隔离。授权条件需要在查询和动作中显式落实。

### 37）HTTP 401/403/404/422/503 的区别？

401 表示需要有效认证；403 表示已知身份无权限；本项目对不可访问对象常用 404，避免暴露存在性；422 是结构或约束不满足；503 是服务暂不可用。应用也会用成功 HTTP 返回业务终止状态，客户端不能只看 200 就认为任务成功。

### 38）单元测试、集成测试、端到端和质量评测区别？

单元测试检查纯逻辑与分支；接口集成测试连数据库但可替换模型；浏览器检查验证交互；真实端到端需要真实接口贯通；质量评测还需要题集、标准答案/证据及人工判断。Mock 能证明分支按预期走，不能证明模型能稳定正确判断语义。

## 5. 光伏实习：简历写了就必须能解释

### 39）用 40 秒说明光伏链路

EMS 经 Kafka 发调节/复归指令，调控云侧校验、幂等落库，再通过 HTTP 对接下游负荷管理系统；下游回调经鉴权后记录结果，再通过 Kafka 回传 EMS。XXL-JOB 做档案/可调资源周期同步、指令重试与结果补偿。此系统不直接控制逆变器，终端执行在下游。

### 40）Kafka 能保证业务绝不重复吗？

不能把 Kafka 的生产幂等或事务等同于外部 HTTP 业务 exactly-once。消费后落库再提交 offset 的窗口可能重复处理，需要指令唯一标识、数据库约束和幂等状态迁移。当前资料描述结果回传为至少一次语义，消费方也要去重。不要凭框架名声称整条链路 exactly-once。

### 41）幂等和锁的区别？

幂等是重复执行的业务效果保持一致；锁是协调并发访问的手段。唯一键、条件更新和状态机可以构造幂等，单纯加锁不解决进程重启后的重复请求，也不能自动解决外部系统的重复执行。

### 42）数据库租约和普通锁有什么不同？

租约有过期时间，持有者崩溃后其他执行器可接管；发送前用原子条件更新争取租约，更新结果要核对 token，避免旧执行者覆盖新执行者。租约时间要覆盖正常操作，长调用需要续租或 fencing 设计。不能把 lease token 误当成对方系统会验证的 fencing token。

### 43）项目的重试边界是什么？

交接资料中：最多向下游发送三次，失败后固定三分钟重试；HTTP 接收成功后等待回调，不因回调慢再次下发控制指令。结果 Kafka 推送失败可由补偿任务重推。该数字属于光伏链路，与 Agent 图的两轮/六次不同。

### 44）HTTP 超时意味着对方没有执行吗？

不意味着。对方可能已接受请求，只是回包丢了。应该使用对方支持的幂等请求号、查询状态或对账，而不是一超时就盲目发新的控制请求。数据库里的本地幂等不能证明外部副作用只发生一次，这是能体现工程判断的重要追问。

### 45）结果落库和发 Kafka 如何保证一致性？

不能靠一个普通本地事务原子提交到两个独立系统。常见方式是事务内记录待发送事件/标记，异步发消息并在成功后更新，失败补偿，接受重复并要求消费幂等。项目有待推送标记和补偿路径，但未据此证明所有故障窗口完全覆盖；需查看具体事务边界与测试。不要擅自说项目用了完整事务 Outbox 或分布式事务。

### 46）哪些知识能迁移到 Agent 岗位？

两者都有状态迁移、重复执行、外部接口超时、补偿与追踪问题。可以讲迁移思路，但 Agent 模型存在随机输出、提示注入与语义质量验收，不能用传统接口状态码替代语义验收。

### 49）动手题：加一个拒答测试

在 `tests/test_agent_workflow.py` 为写作角色返回 `answerable=false` 加场景。预期：不调用审查角色、不返回 claims/citations、status 为 insufficient_evidence。先写预期再运行测试，解释为什么不能直接把拒答当模型失败。

### 50）动手题：看 trace 算调用次数

正常通过：plan→search→write→review，共三次角色模型调用；第一次审查要求 rewrite 再通过，共五次；要求 retrieve 后再通过，共六次。引用第一轮非法第二轮仍非法：plan 一次、write 两次，共三次，不调用审查。拿 Demo 输出逐项对照，不把 search 算进聊天调用计数。

### 51）动手题：权限在 reviewer 返回时被撤销

给 Fake review 加 hook，在返回 accept 前撤掉成员权限。预期请求无权继续、不能新增该用户问答记录，响应中没有草稿和证据。重点是证明“审查通过”不能绕过最后授权，不是只给测试增加一个 assert True。

### 52）动手题：为什么不把预算改成 100？

扩大预算会增加成本、延迟和循环风险。先证明多一轮能修复哪些失败，再用固定题集比较。代码当前刻意限制两轮和六次；随意改数字之前应同步参数校验、前端提示、文档和测试。

### 53）设计题：如果真要做断点恢复？

需要持久化任务 ID、用户/项目范围、阶段与安全中间产物，增加 checkpoint；恢复时重新验证授权、版本与预算；工具副作用要可重入和幂等；处理重复提交和状态竞争。失败草稿是否允许保存要单独做数据保留设计。仅配置 checkpointer 不能替代这些业务规则。

### 54）设计题：如何做“任务拆解”？

复杂问题可先输出有限子问题列表，每项有证据需求与完成条件；对子任务分别授权检索，汇总去重后验收；限制子任务数、深度、并发和总 token。当前没有实现动态子任务拆解器，应作为后续方案解释，不写成已上线功能。
