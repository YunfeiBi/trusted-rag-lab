## 5 你参与时具体做什么

### 按每周约 10 小时安排人工投入

建议每周预留：1 小时集中确认需求与方案，3 小时操作阶段成果并反馈，3 小时阅读原文与核对评测，2 小时理解关键代码及准备讲解，1 小时整理问题和课程材料。可按阶段调整，这是用户的人工时间建议，不是对 AI 执行时长或交付日期的承诺。

AI 按任务台账逐批实现和验证，尽量将人工问题合并到阶段节点。无需用户逐行编写代码，但关键选择和人工验收不能自动替用户完成。

### 六个汇报板块怎样对应真实贡献

| 板块 | 可安排的实际参与任务 | 可记录的贡献 |
| --- | --- | --- |
| 总体架构与项目管理 | 阅读架构并评审一个权限用例，必要时修改一条规则 | 架构评审或实际规则修改 |
| 文档处理 | 核对三份 PDF 的页码、章节和分块；若需编码，修改并验证一项分块规则 | 资料验证或实际解析改进 |
| 检索 | 标注检索题目，运行两组参数；若需编码，修改参数配置及结果输出 | 标注、实验或实际检索配置改进 |
| 可信问答 | 验证越权与无证据场景；若需编码，补充并运行一个回归测试 | 安全验证或实际测试开发 |
| 用户界面 | 实际操作并反馈；若需编码，完成一个状态反馈组件修改 | 交互评审或实际界面修改 |
| 质量评估 | 交叉复核答案证据；若需编码，增加一个指标统计或结果图 | 人工评测或实际评测功能改进 |

以上是待分配建议，不是已完成事实。每项贡献保留执行人、日期、修改或评审记录和验证结果；仅讲解板块时写“负责该板块汇报”，不能写成“完成该模块开发”。最终贡献说明同时包含用户主开发与 AI 辅助的真实范围。

### 开发前一次性提供

- 汇报日期、可投入时间及课程实际验收要求。
- 可以用于演示的公开资料，建议先 3—5 份，跑通后再扩充。
- 部署目标及模型调用预算；现有密钥已经配置，无需再次发到聊天。
- 其他成员真实参与安排及是否仍要求每人代码贡献。

### 每个阶段的人工验收

AI 提交“本轮做了什么、怎样启动、如何检查、自动验证结果、已知限制”。用户按步骤操作，反馈实际现象；问题修复后再验收。

每次验收记录日期、任务 ID、验收人、实际步骤、通过或失败及证据位置。只有用户明确反馈或提交真实记录后，才标记“已验收”。

### 正式评测与汇报

人需要阅读原文确定标准证据，检查回答是否受证据支持，处理争议样例，并真正理解自己要讲解的系统。AI 可辅助起草和统计，不能替代真实阅读或代替本人进行课程汇报。

### 每轮工作的结束动作

1. 核对本轮实际修改与验证结果，不凭聊天承诺更新为完成。
2. 更新任务状态、待确认项及下次起点。
3. 记录关键决策原因、限制、AI 实际参与范围及人工复核状态。
4. 一批可复查成果形成 Git 提交，避免只留在聊天或未保存的缓冲区。
5. 用户授权同步 GitHub 时执行推送并验证远程提交；本地提交不等于已远程备份，汇报时说明两者状态。
